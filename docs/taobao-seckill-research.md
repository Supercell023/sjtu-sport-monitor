# 淘宝限购/秒杀自动抢购：可行性调研

调研时间：2026-11-04 ｜ 目标：判断「限购商品准时抢购」脚本能否实现，先看现成产品

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| GitHub 上有同类产品吗 | 有，几十个，但几乎全部是 2020–2022 年「抢茅台」热潮的产物，多数已停更；仍在维护的只有 `chao325/MaoTai_GUIT`（2148★，2026-10 仍在推）和 `mc-yzy15/TaoBaoGoods`（2026-06） |
| 技术上能实现吗 | 「准时 + 自动下单 + 自动跳付款页」可以实现；「稳定抢到热门限购商品」不能保证 |
| 最稳的路线 | 浏览器内自动化（油猴脚本 / Playwright），复用已登录会话，遇滑块转人工 |
| 最诱人但最脆的路线 | 直接调 mtop 接口，签名 + 设备指纹 + 滑块，一两个月就可能全线失效 |
| 主要风险 | 平台侧：订单被判异常取消、账号限权/封禁；法律侧：**制作、销售**抢购软件已有刑事判例（自用风险低得多，但仍在协议禁止范围内） |

一句话：**能做，但这是个「工程 + 对抗」问题，不是一个脚本问题**。真正决定成败的是库存量、账号资格和风控策略，不是代码写得多快。

### 从这些项目里能确认的三件事

1. **无人声称「长期稳定」**。连 2148★ 的那个都在 README 里写明不保证成功、接口随时变。
2. **共同骨架完全一致**：扫码登录 → 提前进商品页选好规格 → 本地对时 → 到点提交 → 跳付款页。差异只在「用什么提交」。
3. **失败原因高度集中在风控**，不是代码 bug：`Galaxy-gx` 作者的原话是「签名算法好像时不时会变，果然个人的力量没有团队的力量强」，还发现「阿里、腾讯的 ECS 被淘宝通过 whois 识别，只能本地跑」。

## 三、三条技术路线对比

| | 浏览器自动化（油猴 / Playwright / Selenium） | 协议层直连 mtop h5api | 安卓无障碍（Auto.js / Appium） |
|---|---|---|---|
| 原理 | 在真实浏览器里点击、填表、提交 | 自己拼请求，`_m_h5_tk` + sign 签名 | 模拟点击淘宝 App |
| 速度 | 中（受 DOM 渲染拖累，200–800ms） | 最快（50–150ms） | 慢（1–3s） |
| 登录态 | 直接复用浏览器 Cookie，最省事 | 需自己维护 cookie / 设备标识 | 复用 App 登录 |
| 滑块 | 出现时肉眼可见，可转人工 | 直接返回 `FAIL_SYS_USER_VALIDATE`，难处理 | 弹在 App 里，脚本点不到 |
| 维护成本 | 低（改选择器） | **极高**（签名、appKey、风控参数随时变） | 中（版本更新、无障碍权限被收紧） |
| 被识别概率 | 低（就是真人浏览器） | 高（缺鼠标轨迹、指纹、TLS 指纹） | 高（2023 年起淘宝加强了无障碍检测） |
| 适合谁 | 个人自用、单账号、少量场次 | 有逆向能力的团队、多账号 | 只有手机、不想开电脑 |

**给你的建议是第一条**：你现有的 `sjtu-sport-monitor.user.js` 已经证明了「浏览器内 + 对时 + 轮询 + 通知 + 自动下单」这套骨架在自己账号上能跑通，淘宝场景可以复用 80% 的结构，把「查空位」换成「到点提交」。

## 四、淘宝特有的六个卡点（按杀伤力排序）

1. **限购资格本身是门槛，不是速度问题**
   热门限购商品（茅台、显卡、球鞋、演出周边）常见形态是：先预约/抽签 → 中签才有购买资格 → 购买时再拼手速。脚本只能解决最后一环。没有资格，脚本再快也是「秒回无货」。

2. **滑块验证（x5sec）**
   淘宝风控在判定异常时返回 `FAIL_SYS_USER_VALIDATE`，前端跳到 `_____tmd_____/punish?x5secdata=...` 的滑块页。触发因素包括：请求频率、鼠标轨迹缺失、设备指纹陌生、IP 异常（机房 IP 几乎必触发）、账号新注册/低活跃。
   → 现实做法是**检测到就弹窗让人过**，不要试图自动破解（识别率不稳，且属于明确对抗行为）。

3. **下单接口签名（走协议层才遇到）**
   h5 侧公开的通用写法是：从 Cookie 取 `_m_h5_tk`，按 `token_timestamp` 拆出 token，`sign = md5(token + "&" + t + "&" + appKey + "&" + data)`。这套东西**能用，但会变**，且 appKey、接口版本、必填风控参数（如 `umid`、`deviceId`）随时调整。

4. **时间精度**
   秒杀窗口往往是「开售 1–2 秒内售罄」，本机时钟偏差 300ms 就等于出局。需要和服务器对时（NTP `ntp.aliyun.com`，或读接口/响应头里的服务器时间），并在开售前 1–2 秒进入高频轮询。你现有脚本里「读 `Date` 头 + 取 RTT 最小的一次 + 提前 1.5 秒启动」的做法可以直接搬。

5. **提交后的排队与库存分片**
   淘宝下单成功 ≠ 买到，会有短暂的「排队中」，且库存分片到不同仓/不同场次。脚本要能区分「提交成功」「排队」「无货」「被限购」「风控拦截」五种返回，否则会疯狂重试把账号打进风控。

6. **付款环节**
   脚本一般停在收银台。要做「自动付款」就得保存支付密码或走免密，安全风险远大于收益 —— 建议只做到「自动打开付款页 + 推送提醒」。

## 五、合规与风险（必须知道的部分）

- **平台规则**：淘宝《服务协议》《淘宝规则》禁止使用插件、外挂、脚本等非官方工具参与交易。后果是订单被取消、账号被限权/封禁（连带同设备、同支付账号的关联账号）。这是「是否合规」的问题，不是「是否违法」的问题，但代价是实实在在的。
- **刑事风险主要落在「制作/销售」侧**：2017 年太原迎泽区法院判决的国内首例「黄牛抢购软件」案，三名制作者/销售者以**提供侵入、非法控制计算机信息系统的程序、工具罪**获刑（获利 11 万余元）。此后多地有同类判例（裁判文书网可查，如 (2017)晋0106刑初583号）。
  → **自己写、自己用、不售卖、不代抢、不传播**，风险等级和「卖软件/接代抢单」完全不是一个量级。
- 顺带一提：`MaoTai_GUIT` 那种「授权卡密 + 免费软件禁止售卖 + 下载后 24 小时内删除」的组合，本质上是规避责任的写法，别把它当「开源方案」参考。

## 六、如果要做，建议的最小可行方案（v0）

**形态**：Tampermonkey 脚本，跑在你已登录的淘宝/天猫商品页或购物车页。

**只做四件事**（每一件都不碰风控红线）：

1. **对时**：开售前 60 秒开始读服务器时间，取 RTT 最小样本，算出本机偏移。
2. **预热**：提前 N 秒把 SKU、数量、地址选好（限购商品数量锁定 1），停在「提交订单」前一步。
3. **到点提交**：T-1.5s 开始以 300–500ms 间隔点「提交订单」，按返回结果分类处理；遇到滑块/验证页立刻停止重试并横幅+推送提醒（人工接管）。
4. **收尾**：成功则打开付款页 + 推送（Bark/ntfy/Server酱，接口你现有脚本已经写好了）；失败则停止，不无限重试。

**明确不做**：自动过滑块、自动输支付密码、多账号并发、协议层伪造请求、代抢。

**验证顺序**（重要，别一上来就抢真东西）：
- 先拿一个**不限购、库存充足**的商品跑通「到点提交 → 到付款页」全流程（下单后取消）；
- 再拿一个**限购但库存宽松**的商品验证「限购 1 件」时数量控件的行为；
- 最后才是真实热门场次。
